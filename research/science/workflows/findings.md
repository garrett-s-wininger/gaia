# What shared preparation changes in adjacent workflows

The strongest gains remove avoidable work across a declared lifetime. Existing combined/batched APIs often capture most of that opportunity already. Each comparison below belongs to its own five-block workload; differences cannot be added into a platform speedup.

| Workload | Result | Important control/limit |
| --- | --- | --- |
| Three image outputs | Combined ffmpeg 93.19 ms; parallel independent ffmpeg 94.82 ms | The Python decoded-buffer bridge loses at 197.12 ms. Three actual icons/diagrams; no new codec or broad image claim. |
| Native scalar-module session | Retained online 8.13 ms versus fresh hosts 72.44 ms | Existing batched host is faster at 2.73 ms. Only declared state and serial quiescent replacement. |
| Four private source workspaces | Logical/shared 734.49 ms versus private/materialized 2,135.38 ms | Strong hardlink/shared-cache control takes 940.09 ms. One provider process and explicitly admitted edits. |
| Current editor feedback | Cancel-obsolete 26.69 ms versus FIFO 278.45 ms | Controlled queued twelve-edit burst; not a natural typing trace or arbitrary running-task cancellation. |
| Actual upstream documentation tests | Existing batch 203.08 ms; online retained 215.49 ms; repeated fresh interpreters 1,272.48 ms | Real 189-example module subset, not full CPython or application test suites. |

The [asset study](../../../experiments/science/workflows/results/assets/REPORT.md) shows why sharing a decode is insufficient when a wrapper adds processes and copies. The [native study](../../../experiments/science/workflows/results/native/REPORT.md) demonstrates a small execution/update boundary with explicit ABI/version checks, without claiming arbitrary application hot reload.

The [workspace study](../../../experiments/science/workflows/results/workspaces/REPORT.md) separates sharing source facts from omitting filesystem materialization. Its fresh-process memory diagnostic shows only a small RSS difference despite larger logical payload-count differences. The [editor study](../../../experiments/science/workflows/results/editor/REPORT.md) exercises real analysis tasks, queued cancellation and stale-publication rejection. The [test study](../../../experiments/science/workflows/results/doctests/REPORT.md) preserves an existing competent batched API and validates failure recovery and loaded-source identity.

Nine focused tests cover private overlays, atomic hardlink replacement, concurrent expected-generation updates, captured-state lifetime, publication invalidation, syntax errors and actual upstream test execution/generation guards. Sources and measured binaries stay frozen across primary matrices. Logical memory budgets, process RSS and compatibility materialization remain distinct costs.

## Hardware visibility needs a real boundary probe

Sandbox CUDA and Vulkan attempts fail, and device nodes are hidden there. Approved host probing exposes `/dev/dxg`; explicit DXCore adapter selection identifies hardware AMD Radeon 860M Graphics and creates a D3D12 device successfully. A null/default-adapter attempt returns unsupported. Therefore default-provider or sandbox failure does not prove that this machine lacks an accessible GPU. Device creation alone is not a compute or speed result. The [capability record](../../../experiments/science/workflows/results/capabilities.json) preserves those distinctions.

Real D3D12 GPU dispatch is available through explicit DXCore AMD adapter selection. Exact-readback frontier propagation loses to native CSR on the captured Django graph and both generated scales, including dense frontiers. [Hardware results](../../../experiments/science/workflows/devices/results/REPORT.md) include initialization, allocation/upload, synchronization/readback, and negative fallback controls. No crossover against the strong CPU control was observed.
