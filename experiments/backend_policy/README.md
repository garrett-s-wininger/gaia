# Backend policy on genuine source edits

This experiment follows the negative [pass-formulation](../pass_algebra/README.md) and [retained-fact](../pass_algebra/retained/README.md) results by measuring a complete changed-file compile, link and executed regression workload. It uses a private Zstandard 1.5.7 source copy and measures backend policy separately from shared-workspace caching and publication.

The [measured report](results/backend/REPORT.md) records a compile-time win over `-O2`, its runtime/size cost, and the stronger stock development controls.

## Question and intervention

Which part of a genuine compilation miss costs time, and can a cheaper machine-code stage repay any resulting execution slowdown?

The five policies compile the same edited `lib/compress/zstd_lazy.c`:

| Policy | Flags beyond the common context |
| --- | --- |
| Stock unoptimized | `-O0` |
| Stock development optimization | `-Og` |
| Stock level one | `-O1` |
| Stock level two | `-O2` |
| Level two with cheaper machine passes | `-O2 -mllvm -fast-isel=true -mllvm -optimize-regalloc=false` |

The last policy requests LLVM's fast instruction selector, with fallback available, and disables optimized register allocation. It is a bounded use of existing compiler internals, not a new code-generation algorithm or a portable Clang API. The pinned compiler is Clang/LLVM 22.1.8 on x86-64. Explicit fast instruction selection does not mean every instruction avoids the normal selector.

Both level-two policies must emit **byte-identical optimized LLVM IR** for each edit. Their machine code can differ. This separates a machine-code policy change from removing high-level optimizations. Stock `-O0`, `-Og` and `-O1` are essential controls: a policy beating only `-O2` is not automatically the best development choice.

All other library translation units and the regression harness are built once with `-O2`. The common context disables legacy format support and assembly, uses a single-threaded Zstandard build, defines `NDEBUG`, and rejects date/time builtins. The compiler uses its default target, with no `-march=native`. These choices are identical across policies. This is a warm incremental operation with unchanged dependencies already built, not a clean build or a whole-project change of optimization level. `-Og` is evaluated without debug information; debugger quality is not tested.

## Edits and exercised behavior

Two independent edits start from the upstream original:

- `search_budget`: halve the hash-chain search-attempt budget, with a minimum of one attempt. This changes an inline search helper used by multiple specializations.
- `lazy_depth`: increase the no-dictionary hash-chain lazy wrapper's search depth from one to two. This changes one wrapper's algorithm selection.

Each edit must change compressed bytes on at least one exercised case compared with the original. The earlier compiler study's emitted-constant probe established an object-cache miss, but did not change an exercised algorithm; this study uses the stronger workload condition. An initial stride edit was rejected before measurement because this workload did not distinguish its output. No timings from that failed preparation are part of the recorded comparison.

The executable runs an explicitly constructed regression workload through real Zstandard APIs. It covers greedy, lazy, lazy2 and binary-tree lazy2 strategies; row match finding enabled/disabled where applicable; dictionaries present/absent; lengths 0, 31, 4,096 and 65,536; upstream source text and two deterministic generated byte distributions. Each suite has 168 compression/decompression cases. It checks every decompressed byte and emits an archive of compressed frames. Every policy's complete frame archive must exactly equal the **current edit's** stock `-O2` reference. This permits intentional differences between edits and requires equivalent exercised behavior between compilation policies.

The workload is not the upstream conformance suite or a proof of all compiler/Zstandard behavior. It does not cover streaming external dictionaries, multithreaded compression, sanitizers, debugger fidelity or all architecture-specific code. Legacy and assembly are explicitly disabled. No production compiler policy is selected here.

## Clocks, controls and identities

Seven randomized blocks each compile both edits under all five policies: 70 unprofiled requests. These are repeated measurements of forced compilation misses, with no object/result cache enabled. They are not a captured edit history: ordinary cache hits and returns to known source versions are outside this question.

The complete short-operation clock includes writing the edited file, the compiler process, linker process, executable launch, one regression suite and compressed-frame publication. Compile, link and test process spans are also reported. Exact cross-policy archive comparison and object hashing happen after the short-operation clock. The program's decompression checks are inside it.

After that operation, the same executable runs eight suites in one fresh process. This provides a measured execution-cost alternative. `long_demand_sum_ns` replaces the short test span with that longer span; it is an explicit sum of components, not a directly timed uninterrupted compile-and-eight-suites operation. The intervening short run and validation can affect cache warmth. Neither one nor eight suites is claimed to model a measured user-demand distribution.

Archive extraction, fixed-library/harness compilation, reference builds and intrusive profiling are recorded preparation, outside warm-operation clocks. Fixed compilation uses four preparation workers; measured requests are serial and use a shared advisory measurement lock. This excludes cooperating timed cases, not unrelated load or preparation. The compiler, its resolved dynamic libraries, archive, implementation, source tree and fixed artifacts are pinned and checked again after the matrix. The environment is recorded by digest. This is selected tool/input identity checking, not a hermetic SDK or filesystem-observation contract.

Four diagnostic time traces cover the two edits under the two level-two policies. Trace granularity is zero to expose all pass events. Profiles are separate from the uninstrumented timing matrix. `Backend` contains optimizer and machine-code work; pass-manager wrappers contain child passes. Their inclusive durations **must not be added together**. `OptFunction` in this trace belongs to machine-code emission, not a complete function optimization lifecycle.

## Reproduce

Provide a trusted pinned Zstandard 1.5.7 archive, Clang 22, GNU `ar`, and Linux `ldd`/file locking. Use fresh work/output directories; existing directories are rejected.

```sh
python3 experiments/backend_policy/run.py \
  --clang /usr/lib/llvm22/bin/clang \
  --ar /usr/bin/ar \
  --archive /path/to/zstd-1.5.7.tar.gz \
  --work experiments/_work/backend-policy-reproduction \
  --output experiments/backend_policy/results/reproduction \
  --lock /path/shared/measurement.lock \
  --blocks 7 --seed 9181 --long-repeats 8

python3 experiments/backend_policy/analyze.py \
  experiments/backend_policy/results/reproduction
```

The runner checks unique edit anchors, distinct exercised edit outputs, exact policy-equivalent compressed frames, round trips, stable per-policy objects across blocks, identical optimized IR for the two level-two policies, and frozen inputs. Failed subprocesses abort. Raw observations and full time traces are ignored; summaries, validation, provenance and raw identities are retained. The human report interprets those generated artifacts.
