# Existing schema tools already share work, but parallelism still matters

Unmodified `protoc` provides a useful production-tool control for the synthetic schema-sharing prototype. Combining three built-in outputs reduces repeated sequential invocation work. Three independent parallel invocations are faster in both measured source cases, however. A retained descriptor helps one supported case modestly and fails our exact-output contract on the other.

The [official guide](https://protobuf.dev/programming-guides/proto2/#generating-your-classes) documents multiple language output directives in one invocation. This experiment measures that existing capability, not a new Gaia compiler or a claim that a universal shared AST has been established.

## Matched source controls

The installed compiler is `libprotoc 36.1`. Inputs are the actual installed 61,186-byte `google/protobuf/descriptor.proto` and a separate generated 77,323-byte, 250-record/13-field recursive-reference fixture. The three built-in generators emit C++, Java and Python. Their four output files total 4,712,951 bytes for the real descriptor case and 30,572,052 bytes for the generated fixture.

Five shuffled blocks include subprocess startup, tool execution and output writes. Output-directory creation, oracle hashing and Python syntax checks are outside the timed operation for every mode. Each operation acquires/releases the shared measurement lock separately. Host pages are warm and ordinary/residual host load is not excluded by that lock. A separate diagnostic text comparison overlapped part of this run; these are paired observations under that host load, not idle-machine latency guarantees.

| Source-generation operation | Actual descriptor.proto | Generated 250-record fixture |
| --- | ---: | ---: |
| Three independent invocations, sequential | 233.10 ms | 1,355.10 ms |
| Three independent invocations, parallel | 122.54 ms | 927.54 ms |
| One combined invocation | 199.93 ms | 1,276.89 ms |

Combined generation beats sequential independent generation in five/five blocks for the descriptor case and four/five for the fixture. It loses to independent parallel generation in every block for both cases. Sharing front-end work is useful, but does not automatically compensate for serial generation. This does not isolate parsing from generation, I/O or process costs; CPU utilization, RSS and generated C++/Java compilation are not measured here.

## Descriptor handoff must pass output equivalence first

Before sampling any mode, the runner generates a source-based oracle and checks each candidate's exact output hashes. Descriptor readers receive only an empty source directory and the prepared descriptor set, so they cannot fall back to parsing the source files.

The actual descriptor.proto case passes this check for both handoff modes:

| Actual descriptor.proto operation | Median complete request |
| --- | ---: |
| Source generation, three parallel invocations | 122.54 ms |
| Produce descriptor now, then three parallel descriptor readers | 143.24 ms |
| Reuse prepared descriptor, three parallel descriptor readers | 108.53 ms |

The retained descriptor is 78,782 bytes and initially costs 28.45 ms to produce. Retained requests win four/five blocks against parallel source generation. Charging first descriptor production loses all five. Each reader still decodes its own descriptor model; this is not shared in-memory AST access or a complete preparation-amortization proof.

The generated fixture **fails** both descriptor-handoff preflights. All four generated C++/Java/Python output files have different hashes. For example, source-based `cpp/fixture.pb.cc` is 8,516,937 bytes, versus 8,988,487 after descriptor handoff. Its first differing byte is at offset 36,777: an otherwise implicit field JSON name appears as an explicit `json_name` annotation in generated text. Serialized Python descriptor bytes differ too. The prepared model is 299,239 bytes and cost 53.35 ms to produce.

This reproduces the original failed exact-output guard. The mismatch is retained with source/model/output hashes and short byte contexts in [rejections](rejections.json) and ignored raw observations. No output normalization, removal of annotations or weakened oracle is applied. Those modes are excluded from timing the fixture. Different generated bytes are a failure of this experiment's representation contract; this result alone does not prove the generated programs behave differently. A weaker semantic-equivalence contract would need its own evidence.

## Correctness, failures and provenance

All 40 timed operations match their source oracle exactly, and each generated Python file passes compilation as a syntax/code-generation check. C++/Java outputs are not compiled or executed. Input source, prepared descriptors, runner source and compiler binary identities are checked unchanged after the run. The initial source/model/output artifacts remain in ignored work directories for local inspection.

The runner checkpoints observations after each completed operation and records exceptions before exiting. A separate [injected producer-failure check](failure-check.json) preserves the first case's five completed measurements plus its error record when second-case preparation fails. These JSON checkpoints are not a crash-durable journal or a guarantee against interrupted output-file writes.

[Summary](summary.json), [validation](validation.json), [provenance](provenance.json) and [raw identity](raw-identity.json) identify the ignored `results.json`. This run uses the existing Linux developer laptop. It is not a standalone speedup claim for the surrounding Gaia toolchain.

## Reproduce

Run from the repository root with an installed compatible Protobuf compiler/development schema, Python and a fresh work/output directory. Choose your own disposable paths; generated models and code do not belong in source history.

```sh
python3 -B experiments/workflows/protoc_baseline.py \
  --protoc "$PROTOC" --descriptor "$DESCRIPTOR_PROTO" \
  --work "$WORK/protoc" \
  --output "$OUTPUT/protoc" \
  --trials 5 --lock "$MEASUREMENT_LOCK"
```

The source fixture and its input hashes are recorded in raw evidence. `--lock` is optional for a standalone run. Unsupported descriptor modes are reported explicitly, while the three source-generation controls remain required. A useful next prototype would retain one immutable interpretation while running independent generators concurrently; it must preserve the explicit/implicit metadata distinctions revealed here.
